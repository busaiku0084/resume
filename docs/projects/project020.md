## プロジェクト概要

メールコンテンツ作成システム（ビジュアルメールエディタ）のPhase 3として、EC2上で稼働するPHP（Laravel）製のバックエンドを、TypeScript（Hono）+ AWS Lambdaのサーバーレス構成へリプレイスするプロジェクト。フロントエンドリプレイス（Phase 1）、認証基盤連携（Phase 2）に続くフェーズで、あわせて外部システムからエディタを単体利用し完成HTMLを受け取れる機能を追加した。

リリースは段階移行ではなく一括切替が前提のため、既存の全40 APIのレスポンス形状・ステータス・エラーまで旧バックエンドと完全に一致させることが必須条件だった。新旧バックエンドの挙動を自動比較する仕組みを設計し、40ルート中37ルートの移植と、方式設計（ADR 15本を起票）を担当した。


## チーム情報

チーム人数：3名（開発3名）
役割：バックエンド移植の主担当・方式設計


## 開発・実装内容

#### 開発基盤・方式設計

- フロントエンドとバックエンドをpnpmワークスペースのモノレポに統合し、zodスキーマを契約の唯一の正（SSOT）としてOpenAPI 3.1を自動生成する仕組みを構築。FE/BE間の契約のズレをCIで検出
- DBスキーマ変更を「追加のみ」に制限するルールを定め、それを機械的に検査するマイグレーションlintを自作してCIに組み込み（切替後も旧環境へ即時ロールバックできる状態を担保）
- ORMを使わず、Repositoryのinterface・インメモリ実装・MySQL実装の3点セットで構成するレイヤ設計。ドメイン層は旧バックエンドの処理単位と1対1で対応させ、移植の追跡性を確保
- 認証基盤（JWT/JWKS検証、発行元レジストリ、契約/サービスの2階建て内部ID）をPHPからTypeScriptへ移植。JWKSのキャッシュ・バックオフ・レート上限を自前で制御し、過去の実障害への対策を維持

#### 新旧バックエンドのパリティテスト基盤

- 新旧バックエンドに同一のHTTPリクエストを流してレスポンスを比較するテストハーネスを設計・実装。ルート台帳はコードを正とし、レビュー用ドキュメントを自動生成
- レスポンスだけでなく、DBの書き込み結果やS3への書き込み結果も比較する多段階の検証に拡張
- DB比較方式を共有DBの復元方式から新旧で独立したDBを持つ方式へ移行。両DBの初期状態を行数と全列CRCで照合し、不一致なら停止するfail-closedな設計とした

#### ドメイン移植（40ルート中37ルートを担当）

- コンテンツ・画像・テンプレート・一時データの4ドメインを移植。S3操作をストレージ層に切り出し、書き込み系はトランザクションで整合性を担保
- 旧バックエンドのHTML出力をバイト単位で再現する互換モードを実装（libxml特有の挙動を含めてPHP実装を忠実に移植）
- Laravelのバリデーションやエラー形式の差異を棚卸しして修正。form-encodedリクエストの互換対応で見つかったプロトタイプ汚染も修正

#### 単体利用機能・インフラ

- 外部システムからエディタを起動し、完成HTMLをサーバー間認証（OAuth 2.0 client_credentials）で取得するAPIを実装。CSSのインライン化層を追加
- 単体利用時にクライアントの認証基盤（Keycloak）でのログインを必須化（OIDC 認可コードフロー + PKCE）。外部IdPのトークンは本人確認後すぐに破棄する設計
- 検証用の外部サービスのモックをLambda + 関数URLで構築し、別のCDKアプリとして分離。予約同時実行数の制限で本体APIの実行枠を保護
- AWS CDKでAPI Gateway（カスタムドメイン）・Lambda・SSM Parameter Store（秘匿値の実行時取得）などを構築。ステージング環境・検証環境の構築手順書を整備


## 課題・問題点

- 一括切替が前提のため、全40ルートが旧バックエンドと挙動互換であることを証明する必要があったが、旧バックエンドのテスト規模は大きく、人手のレビューだけでは保証が困難だった
- レスポンスが同じでもDBの状態が異なるケースがあり、過去に障害も発生していたため、HTTPレベルの比較だけでは不十分だった
- 共有DBを復元する比較方式は、バッファ長・パケットサイズなどの制限に次々と抵触し、構造的に破綻していた
- 旧バックエンドのHTML出力はライブラリ特有の挙動に依存しており、出力を完全に一致させる難易度が高かった
- 3ヶ月・3名という限られた体制で、移植・新機能・インフラ刷新を並行して進める必要があった


## 工夫・思考プロセス

- 移植の完了条件を「パリティテストがgreen」と明確に定義し、移植済みルート数を数値で追跡できるようにして進捗とリスクを可視化した
- 共有DB方式の限界を実測で見極めた上で独立DB方式へ切り替え、実機で判明した罠（チェックサムがインスタンス間で一致しない、タイムゾーンやsql_modeの差異など）は記録して再発を防いだ
- 同じ漏れが繰り返し起きたテスト上の不変条件は、静的検査のテストで固定して仕組みで防止した
- 設計判断はADRとして15本起票し、3名体制でも判断の根拠と経緯を共有できるようにした
- AIエージェント（Claude Code）を前提とした開発フローを整備し、レビューエージェント・pre-pushチェックを組み合わせて品質と開発速度を両立した


## 成果

- 全40ルートのTypeScript移植を完了（うち37ルートを担当）。パリティテストはfullモードで38/40通過・失敗0を維持
- バックエンドのテストファイル222本、パリティテスト43本を整備し、一括切替に向けた互換性の根拠を数値で示せる状態を構築
- 単体利用のAPI・認証フロー・導入手順書をそろえ、ステージング環境を構築。本番切替に向けて移行リハーサルの段階まで到達


## 使用技術（まとめ）

- **プログラミング言語**: TypeScript, PHP（旧バックエンドの読解・移植元）
- **フレームワーク**: Hono, React, Vite
- **契約・バリデーション**: zod, OpenAPI 3.1（zod-to-openapi）
- **認証**: JWT/JWKS（jose）, OIDC（PKCE）, OAuth 2.0 client_credentials, Keycloak
- **DB**: MySQL（Amazon RDS）, mysql2
- **インフラ**: AWS（Lambda, API Gateway, RDS, S3, CloudFront, SSM Parameter Store, VPC）, AWS CDK
- **テスト・品質**: Vitest, MSW, Biome, knip
- **CI/CD**: GitHub Actions
- **モノレポ**: pnpm workspace
- **バージョン管理**: Git（GitHub）
